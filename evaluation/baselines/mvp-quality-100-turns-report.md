# MVP 이용가이드 100턴 품질 평가

## 결론

현재 답변 보류가 전반적으로 과도하다고 보기는 어렵다. 실제 100턴 중 16턴이 보류됐지만,
교정한 기준에서 보류돼야 하는 질문이 15턴이었다. 답변 가능한 85턴 중 잘못 보류된 것은
2턴(2.4%)이다.

상태·보류 사유·문맥·출처 자동 판정은 96/100턴이 기대와 일치했다. 원문과 답변을 수동으로
대조한 결과 자동 판정이 놓친 오답·불완전 답변 3턴을 추가로 확인했고, 최종적으로 94/100턴을
정상으로 판단했다.

## 실행 조건

- 실행 대상: `e678e669e13c1077e00c6b949053dfd560bde2cb` 기반 현재 작업 트리
- 실행 방식: in-process, 케이스마다 새 대화
- 데이터: ACTIVE index 1938, 공식 이용가이드 39개 문서
- 모델: Query Rewrite/Generation `gpt-5.4-mini`, Embedding `text-embedding-3-large`
- 프롬프트: Query Rewrite v4, Source Planning v13, Answer v19, Generation v22
- 구성: 단일턴 60개 + 2턴 대화 20개 = 총 100턴
- 최초 실행: `mvp-quality-v1-100-turns.json`
- 기대값 교정 후 재채점: `mvp-quality-v2-rechecked-recheck-20260907T165121Z.json`

최초 실행 뒤 원문과 질문 의도를 다시 확인해 MQ037, MQ040, MQ068, MQ079의 기대값만
교정했다. 제품 출력은 다시 생성하지 않았으며 v2 결과는 저장된 응답과 DB snapshot을
오프라인으로 재채점한 것이다.

답변 가능 문서가 있는데도 보류됐다. 답변 가능한 질문 기준 불필요한 보류율은 2/85(2.4%)다.

## 판단과 다음 우선순위

현재 핵심 문제는 보류량 자체보다 **답을 했을 때 반대 결론을 내리는 오류**다. MQ015처럼
직접 근거가 Top-1에 있는데도 덜 직접적인 Source를 선택해 잘못 답하는 경우를 가장 먼저
다뤄야 한다.

1. MQ015의 직접 Source 우선 선택과 반대 결론 방지, bare `SOURCE_n` 검증을 함께 분리 검토한다.
2. MQ063의 Query Rewrite exact-match 교정 실패가 사용자 HTTP 500으로 끝나지 않도록 한다.
3. MQ001·MQ027·MQ066의 Top-5 누락을 쿼리별로 분석해 검색 개선 범위를 정한다.
4. MQ040처럼 질문의 수치·상한을 예시로 대체하지 못하도록 근거 충분성 기준을 보강한다.

한 번씩 실행한 진단 세트이므로 비결정성까지 확정한 결과는 아니다. 이번 결과만으로 프롬프트와
검색을 한꺼번에 수정하지 않고, 각 실패를 고정 입력으로 재현한 뒤 담당 단계별로 수정하는 것이
안전하다.

## MQ015 수정 결과

- Generation v24 / Source Planning v15 / Answer v20에서 접근 권한·공개 범위 질문의
  대상 전용 제한·예외 Source와 검색 상위 Source를 우선하도록 보강했다.
- 상위 공간 접근 제한을 내부 프로젝트의 별도 허용으로 추측하지 않도록 Planning과 Answer에
  같은 원칙을 적용했다.
- 올바른 `[SOURCE_n]` marker 밖에 남은 bare `SOURCE_n`은 Backend 검증 실패로 처리한다.
- 첫 강화안 v23은 3/5였고, 선택 우선순위를 명확히 한 최종 v24는 5/5 통과했다. 최종 5회
  모두 `비공개 팀 > 접근 권한`을 선택하고 접근 불가 결론을 냈다.
- 회귀 기준은 단순 `COMPLETED`가 아니라 접근 불가 결론과 `비공개 팀` Citation을 함께
  요구하도록 `mvp-quality-v3`로 올렸다.

## MQ063 수정 결과

- Query Rewrite v7은 최근 유효 5턴을 시간순 후보로 제공하고, 실제 문맥으로 사용한 턴 하나를
  `selectedTurnNo`로 반환한다.
- `contextPhrase`는 선택한 턴의 userQuery/resolvedQuery를 우선 사용하되, 현재 질문이 이전
  답변의 대상을 직접 가리킬 때는 answerContent의 정확한 문구도 허용한다.
- Backend는 선택 번호의 후보 포함 여부, 선택한 턴에서의 문구 출처, 최종 resolvedQuery의
  문구 보존을 모두 검증한다.
- 이름 없는 지시어는 최신 턴을 우선하고, 과거 대상이나 순서를 명시한 경우에만 더 오래된 턴을
  선택한다. 후보와 최신 턴을 중복 전달하지 않아 최신 턴 편향도 제거했다.
- 구조 출력이 두 번 실패하면 ModelCall은 FAILED로 기록하되 사용자 턴은 HTTP 500 대신
  `AMBIGUOUS_QUESTION` 보류로 안전하게 마감한다.
- 최종 v7 표적 평가에서 MQ063 5/5, 최신 턴 보호 MT18 5/5, 명시적 과거 턴 선택 MT19 5/5를
  모두 통과했다.

## 잔여 사례 재검증과 MVP 결정

- 검색·RRF 설정을 변경하지 않은 현재 코드로 MQ001·MQ027·MQ066을 각각 5회 재실행했다.
  결과는 `mq001-mq027-mq066-current-targeted.json`에 보존했다.
- MQ001은 Generation v24 상태에서 5/5 통과했다. 매번 `워크스페이스 > 개요`를 선택해
  워크스페이스를 하나의 조직으로 설명했으므로 추가 수정 대상에서 제외했다.
- MQ027은 0/5였다. 정답 `실행: 작업 > 외부 공유`는 Vector 7위지만 BM25 14위로 후보
  절단 뒤 한쪽 점수만 반영되어 RRF 최종 12위가 된다.
- MQ066은 turn 1이 5/5 통과했지만 turn 2가 0/5였다. Query Rewrite는 매번 백로그 문맥을
  올바르게 복원했고, 정답 `계획: 백로그 > 작업으로 전환`도 Vector 2위로 검색됐다. 다만
  BM25 Top-10 밖이라 RRF 최종 6위에 머물러 Generation Top-5에 포함되지 않았다.
- MQ027·MQ066은 문서나 Query Rewrite 누락이 아니라 RRF Top-5 절단의 알려진 한계다.
  세 사례만을 위해 검색 단위·RRF·Top-5를 변경하면 기존 검색 품질에 회귀가 생길 수 있어
  이번 MVP에서는 수용하고 추가 수정하지 않는다.
- MQ040은 원문이 설정 가능한 최대값 없이 3개 예시만 제공하지만 이를 최대값 질문의 근거로
  사용할 수 있는 Planning/Answer 한계다. 추가 프롬프트 수정과 재평가 없이 이번 MVP의
  알려진 한계로 함께 수용한다.
- 위 결정에 따라 100턴 전체 유료 평가는 다시 실행하지 않는다. MQ027·MQ066·MQ040은
  해결 완료가 아니라 의도적으로 남긴 알려진 한계로 해석해야 한다.
