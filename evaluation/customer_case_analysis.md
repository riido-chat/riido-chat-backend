# 실제 고객 상담 기반 RAG 평가 분석

## 1. 분석 기준

- 원본은 개인정보 처리가 완료된 채널톡 종료 상담 HTML 100건이다.
- HTML의 `question`과 `answer`는 여러 메시지를 단순 결합한 표시용 값이므로 평가 입력과 정답으로 사용하지 않는다.
- 실제 발화 순서와 역할은 `conversation[]`를 기준으로 확인한다.
- 과거 상담원 답변은 당시 운영 상황을 이해하기 위한 참고 자료일 뿐 정답으로 간주하지 않는다.
- 답변 가능 여부와 Citation 기대값은 현재 ACTIVE index의 공식 이용가이드를 기준으로 판정한다.
- MQ027, MQ040, MQ066은 합의된 MVP 한계이므로 이번 평가와 개선 범위에서 제외한다.

## 2. HTML 구조

| 항목 | 확인 결과 |
| --- | ---: |
| 상담 레코드 | 100 |
| 전체 메시지 | 914 |
| 고객 메시지 | 299 |
| 상담원 메시지 | 309 |
| 봇 메시지 | 306 |
| 고객 메시지 1개인 상담 | 32 |
| 고객 메시지 2개 이상인 상담 | 68 |
| 봇 요약이 포함된 상담 | 90 |

모든 레코드는 `sample_id`, `question`, `answer`, `conversation`, `closed_at`,
`medium_type` 필드를 가진다. `closed_at`은 모두 `<날짜>`로 마스킹되어 있어 상담 간격이나
문서 버전과의 시간적 정합성은 확인할 수 없다.

## 3. 평가 단위

상담 한 건과 평가 케이스 한 건을 동일하게 취급하지 않는다.

1. 상담원의 답변 전에 연속해서 입력된 고객 메시지는 하나의 의도로 병합할 수 있다.
2. 이메일, 연락처, 워크스페이스명처럼 상담원이 요청한 식별 정보는 평가 질문에서 제거한다.
3. `감사합니다`, `확인했습니다`, 해결 완료 알림은 독립 질문으로 만들지 않는다.
4. 한 상담 안에서 주제가 바뀌면 별도 의도로 분리한다.
5. 이전 대상이 없으면 해석할 수 없는 질문만 후속 질문으로 분류한다.
6. 현재 질문만으로 검색어가 완결되면 같은 상담 안에 있어도 `NEW_TOPIC`으로 분류한다.

실행 입력은 핵심 어휘, 구어체, 오타와 문제 상황을 유지하되 인사, 감사, 개인정보 전달과
상담 처리 확인을 제거한 정제 문장이다. `<서비스명>`은 대상이 유일한 경우 `뤼이도`로
치환하지만 `<외부서비스명>`은 임의로 Slack, Discord, Github 등으로 복원하지 않는다.

예를 들어 faq-047의 첫 질문은 연동 장애라 공식 문서만으로 원인을 알 수 없지만,
두 번째 질문의 “캘린더가 미팅에서만 연동되는가”는 현재 질문만으로 완결되고 공식 가이드에
직접 근거가 있으므로 새 주제의 답변 가능 질문으로 분리한다.

## 4. 실제 사용자 표현과 반복 패턴

정규식 기반 표면 집계이며 유형끼리 중복될 수 있다.

| 패턴 | 포함 상담 수 | 대표 표현 |
| --- | ---: | --- |
| 계정 탈퇴·삭제 | 19 | `탈퇴`, `회원탈퇴 로직이 보이지 않습니다` |
| 결제·요금제·구독·환불 | 25 | `자동 결제가 되는줄 몰랐네요` |
| 외부 연동 | 18 | `깃헙 연동하고 pr 보냇는데` |
| 오류·동작 이상 | 21 | `업데이트 버튼도 무반응` |
| 기능 제안·개선 | 13 | `이런식으로 수정해주실 수 있나요?` |

기존 합성 평가 질문과 다른 특징은 다음과 같다.

- 띄어쓰기, 오타, 영문 약어와 한국어가 섞인다.
- `탈퇴`, `브랜치명 변경`처럼 문장 형태가 아닌 입력이 많다.
- 현재 증상, 이미 시도한 방법, 사용 환경, 사용자의 추측이 한 메시지에 함께 들어간다.
- 긴 인사와 배경 설명 뒤에 실제 질문이 한두 문장만 등장한다.
- 가능 여부, 실제 처리 요청, 장애 신고, 기능 제안이 같은 문장 형태로 표현된다.
- 한 상담이 끝나기 전에 완전히 다른 질문으로 전환되는 사례가 있다.
- 상담원의 확인 질문에 대한 짧은 답은 독립적으로 의미가 없지만 문맥 정보로는 중요하다.

## 5. 현재 가이드 기준 답변 가능성

100개 상담의 1차 판정은 다음과 같다.

| 판정 | 상담 수 | 의미 |
| --- | ---: | --- |
| `ANSWERABLE` | 9 | 현재 공식 가이드에 직접 근거 존재 |
| `ANSWERABLE_POLICY_ONLY` | 9 | 일반 정책은 답변 가능하지만 실제 계정 처리·예외 승인은 불가 |
| `MIXED` | 13 | 한 상담에 답변 가능·불가능 의도가 함께 존재 |
| `UNANSWERABLE` | 53 | 제품 관련이나 현재 가이드에 직접 근거가 없거나 운영 상태 확인 필요 |
| `AMBIGUOUS` | 5 | 현재 입력만으로 대상 또는 의도를 확정할 수 없음 |
| `OUT_OF_SCOPE` | 2 | 제품 이용가이드 범위 밖의 질문 |
| `UNKNOWN_MASKED_ENTITY` | 6 | 외부 서비스 마스킹 때문에 기대 근거를 확정할 수 없음 |
| `UNUSABLE` | 3 | 전체 마스킹 또는 첨부 화면 부재로 재현 불가 |

위 수치는 상담 단위 판정이라 의도별 실행셋의 완료·보류 분포와는 다르다.

### 답변 가능한 대표 사례

- faq-016: 작업과 하위작업의 구조
- faq-024, faq-067: 워크스페이스 사용자 시트 기준 요금
- faq-026, faq-035, faq-063: 현재 구독 취소·환불 정책
- faq-027, faq-058: 백로그 정의
- faq-047: 구글 캘린더가 미팅만 동기화하는 범위
- faq-048: 뤼이도 서비스 소개
- faq-064: 작업 관계도 드래그 이동
- faq-079: 미팅과 회의록 작성
- faq-083, faq-084: 구독 취소 방법

### 원문만으로 답하기 어려운 대표 사례

- 계정 탈퇴와 계정 삭제 실행
- 특정 워크스페이스의 결제 완료·취소·환불 상태 조회
- 버튼 무반응, 404, 빈 화면, 권한 오류의 실제 원인
- 특정 결제의 예외 환불, 카드 해지, 무료 기간 연장
- 기능 추가 요청과 향후 로드맵
- 과거 담당자와의 개별 약속 이행 여부

제품 관련 질문이지만 근거가 없는 경우 현재 정책에 따라 `INSUFFICIENT_EVIDENCE`로
보류한다. `llm에 대해서 알려주ㅗ`처럼 제품과 무관한 질문만 `OUT_OF_SCOPE`으로 분류한다.

## 6. 데이터 제약

### 외부 서비스 마스킹

`<외부서비스명>`은 개인정보는 아니지만 원본에서 마스킹되어 있다. Slack, Discord,
Github처럼 서비스별 가이드가 다른 상황에서 이를 추측 복원하면 실제 사용자 문장을 평가한다는
목적이 훼손된다.

- 사용자 발화에 서비스명이 남아 있으면 그대로 사용한다.
- 서비스명을 몰라도 질문과 기대 근거가 유일하면 사용할 수 있다.
- 서비스에 따라 정답이 달라지면 `UNKNOWN_MASKED_ENTITY`로 분리한다.
- 마스킹 때문에 발생한 검색 실패는 Retrieval 결함으로 집계하지 않는다.

### 과거 정책과 현재 정책

과거 상담에서 실제 환불이 처리된 사례가 많지만 현재 가이드는 구독 기간 중 환불을 제공하지
않는다고 명시한다. 날짜가 마스킹되어 당시 정책을 복원할 수 없으므로 현재 RAG 평가는 현재
가이드 정책을 기준으로 한다. 실제 환불 처리 결과는 정답이나 기대 동작으로 사용하지 않는다.

## 7. 생성한 실행 후보

`customer_support_cases.json` v1에는 첫 실행 당시 43개 케이스, 51개 턴을 구성했다. 최소 개선
검증 과정에서 실제 변형 질문 `뤼이도가 뭐야?`를 RC044로 추가해 v2는 44개 케이스,
52개 턴이 되었다. 남아 있던 즉시 실행 가능 원본 26건을 RC045~RC070으로 추가한 현재 v3는
70개 케이스, 80개 턴이다.

| 항목 | 수 |
| --- | ---: |
| 단일턴 케이스 | 60 |
| 멀티턴 케이스 | 10 |
| 기대 `COMPLETED` | 16턴 |
| 기대 `WITHHELD` | 64턴 |

완료 질문만 고르지 않고 다음 음성 케이스를 의도적으로 포함한다.

- 공식 문서가 답할 수 없는 장애 문의
- 계정별 상태 조회와 처리 요청
- 일부만 근거가 있는 복합 질문
- 의미가 부족하거나 범위 밖인 질문
- 후속 질문처럼 보이지만 현재 질문만으로 완결되는 새 주제

현재 버전은 첫 실행 결과까지 사람이 다시 판정한 평가셋이다. 정책 설명과 실제 조작 절차를
구분하며, 문서에 취소 가능 여부만 있고 실제 메뉴·클릭 경로가 없으면 방법 질문에는 답하지
않는 것으로 확정했다.

### 1차 수동 기대값 검토 결과

- 하위작업의 구조는 문서에 있지만 UI의 태그 표시 목적과 무한 계층을 막기 위한 설계 의도는
  문서에 없으므로 faq-016의 두 턴을 모두 `INSUFFICIENT_EVIDENCE`로 확정했다.
- 구글 캘린더가 미팅만 동기화한다는 사실은 문서에 있지만, 그렇게 제한한 이유는 없으므로
  이유까지 요구하는 faq-047의 후속 질문은 `INSUFFICIENT_EVIDENCE`로 확정했다.
- 스프린트 기간 표시 질문은 독립적으로도 이해할 수 있지만 앞 턴의 스프린트 일정 등록과
  동일한 대상을 이어 묻는다. 앞 턴을 선택해도 검색 의도를 오염시키지 않으므로
  `FOLLOW_UP_WINDOW`로 확정했다.
- 기술문서 검색 질문의 `업무 공유 문서로는`은 앞 턴의 기술문서·위키 관리 문맥을 받는다.
  대시보드 링크 기능도 외부 리소스를 모아 관리하는 직접 근거이므로 `FOLLOW_UP_WINDOW`와
  `대시보드` Citation을 허용했다.
- 환불 가능 여부를 일반적으로 묻는 질문은 현재 공식 환불 정책으로 답할 수 있어
  `COMPLETED`를 유지했다. 특정 계정의 환불 실행이나 처리 상태 확인은 `WITHHELD`로 구분했다.
- 구독 취소 방법은 현재 문서에 관리자 취소 가능 여부와 적용 시점만 있고 실제 조작 경로가
  없으므로 faq-043, faq-083, faq-084를 `INSUFFICIENT_EVIDENCE`로 확정했다.
- 회의록 작성 위치는 미팅뿐 아니라 에디터와 문서 템플릿도 직접 근거가 될 수 있어 허용
  Citation 범위를 넓혔다.

## 8. 실행 후 진단 기준

| 관측 | 원인 단계 |
| --- | --- |
| 필요한 정답 Section이 Hybrid Top-5에 없음 | Retrieval |
| 후속 대상, 선택 턴 또는 새 주제를 잘못 판정 | Query Rewrite |
| Top-5에 근거가 있지만 답변 가능 여부나 Source 선택이 잘못됨 | Source Planning |
| 선택 Source는 맞지만 사실, 범위, 보류 또는 Citation이 잘못됨 | Answer |
| 현재 공식 가이드에 핵심 정보 자체가 없음 | 원문 부재 |
| 마스킹으로 검색 대상을 확정할 수 없음 | 데이터 제외 |

첫 실행은 각 케이스를 한 번만 수행한다. 실패가 관측되면 원문과 단계 trace를 수동 검토하고,
실제 제품 결함으로 확인된 케이스만 반복 실행해 변동성을 확인한다. 확인되지 않은 가설을 위해
제품 코드나 프롬프트를 먼저 변경하지 않는다.

## 9. 51턴 첫 실행 결과

- 실행 파일: `evaluation/baselines/customer-support-v1-first-run.json`
- 기대값 보정 후 재판정 파일: `evaluation/baselines/customer-support-v1-first-run-rechecked-recheck-20260908T152301Z.json`
- 실행 방식: 로컬 DB를 사용한 in-process 실행, 각 케이스 1회
- 실행 오류: 0건
- 최초 기대값 기준: 43개 케이스 중 32개 통과, 11개 실패
- 결과 수동 판정 후: 38/43 통과, 기대값 문제 6개, 실제 RAG 개선 후보 5개

기대값 문제는 RC005의 지나치게 구체적인 rewrite 키워드, RC016·034·035의 원문보다 넓은
답변 가능 판정, RC032의 Citation 범위 누락, RC043의 문맥·Citation 범위 누락이었다.
RC042는 문맥 기대값만 보정했으며, 근거에 없는 “표시 위치”를 답한 문제는 그대로 실패로
남겼다.

| 케이스 | 관측 | 1차 원인 단계 | 판정 |
| --- | --- | --- | --- |
| RC001 | `탈퇴방법`을 의미 불명확으로 보류 | Source Planning | 계정 탈퇴라는 통상적 의도는 식별 가능하므로 원문 부재 보류가 더 적절 |
| RC019 | 서비스 소개 대신 Discord 연동으로 서비스 전체를 정의 | Retrieval | 소개 Section이 Top-5에 없고 좁은 연동 문서로 과잉 답변 |
| RC027 | 작업 관계도 이동 근거가 Top-1인데 보류 | Source Planning | 드래그 이동 근거를 질문의 `다른 시점`과 연결하지 못함 |
| RC038 | 개별 프로그램 무료 종료일 대신 일반 취소 정책만 답변 | Source Planning | 답할 수 없는 핵심 범위를 일반 정책으로 축소 |
| RC042 | 설정 위치를 전체 기간의 표시 위치라고 답변 | Source Planning | 설정·관리 근거를 조회·표시 근거로 확장 |

RC019는 Retrieval이 1차 원인이며 Source Planning이 좁은 문서를 거부하지 못한 2차 문제가
있다. RC042는 Source Planning이 답변 범위를 잘못 승인한 뒤 Answer가 `관리`를 `확인`으로
확장했다. 나머지 통과 케이스의 답변과 Citation에서는 별도 수정이 필요한 오류를 확인하지
못했다.

위 5개를 각 3회 반복한 결과는 케이스 실행 기준 6/15 통과였다. RC019와 RC027은 3회 모두
실패했고, RC038은 2회, RC042는 1회 실패했다. RC001은 3회 모두 통과해 최초 실행의 일회성
변동으로 판정하고 수정 대상에서 제외한다.

반복 실행으로 확정한 최소 개선 범위는 다음과 같다.

1. RC019: 짧은 서비스 정의 질문에서 `소개` 문서가 Top-5에 들어오도록 Retrieval을 진단한다.
2. RC027: 직접 근거를 선택하고도 Answer가 보류하는 단계 간 불일치를 포함해 생성 프롬프트를
   최소 보강한다.
3. RC038·RC042: 계정별 사실이나 표시 위치처럼 문서에 없는 핵심 질문을 일반 정책·설정
   위치로 축소하지 않도록 Source Planning의 범위 보존 규칙을 보강한다.

MQ027, MQ040, MQ066은 이 과정에서도 제외한다.

## 15. #171 Query Rewrite 잔여 사례 진단과 v10 검증

RC005/2·RC042/2·RC065/2를 한 이슈에서 진단했다. RC005/2는 `이렇게` 자체보다 현재 질문에서

`스프린트 일정`과 표시 위치 의도가 현재 질문에 모두 있어 이전 턴이 필요하지 않다. RC065/2는
`해당 버튼`이 이전 턴의 Action 설정을 가리키므로 상위 외부 레포 연동 범위와 Action을 모두
보존해야 한다.

Query Rewrite v10은 세 경계를 예시와 최종 판정 규칙으로 명시했다. Backend에는 모델이 선택한
context phrase가 이미 현재 질문에 존재하고 명시적인 과거 참조도 없는 경우 `NEW_TOPIC`으로
정규화하는 규칙을 추가했다. 또한 검증을 통과한 재작성에 `해당 버튼`, `그 메뉴`, `그 설정` 같은
잔여 지시 표현이 있으면 구체 문맥은 유지하면서 일반 명사로 정규화한다.

첫 5회 반복에서는 세 사례의 Query Rewrite 기준은 15/15였지만 Source Planner가
`WITHHELD`·`RELATED_GUIDANCE` 사이에서 변동해 전체 기준은 11/15였다. 같은 기능의 공식
