# 운영 재색인과 테스트 corpus 준비

문서 그룹별 재색인은 이미 데이터베이스에 `READY`로 저장된 문서만 대상으로 한다. 재색인 스크립트는 외부 GitBook을 다시 읽거나 파일 corpus를 교체하지 않고, 실행 중인 앱의 그룹별 색인 API를 호출한 뒤 성공한 그룹만 메모리 corpus를 다시 적재한다. 한 그룹이 실패해도 나머지 그룹은 계속 처리하며, 마지막에 실패한 그룹이 있으면 명령은 실패한다.

배포 후 원격 개발 환경을 준비하는 순서는 다음과 같다.

1. 애플리케이션을 배포하고 Alembic을 `20260911_11`까지 적용한다. 이 마이그레이션은 `20260908_10`에 의존한다.
2. 승인된 원격 개발 DB에서 [`ops/bootstrap_testing_corpus.sql`](../ops/bootstrap_testing_corpus.sql)을 한 번 실행한다. 이 SQL은 이미 존재하는 `HELP_CHATBOT_TEST` 그룹을 확인하고 `HELP_CHATBOT`의 `TESTING` revision을 Terra v24 / rewrite mini v7 / cache false로 맞춘다. 그룹이나 corpus 행은 만들지 않는다.
3. 같은 애플리케이션 이미지와 설정으로 `python -m app.ops.bootstrap_testing_corpus`를 실행한다. 이 명령은 production ACTIVE index의 READY 문서와 관계된 node, chunk, embedding을 target 소유 행으로 복사하고, target에 별도의 ACTIVE index를 만든다. 생성된 identity와 공유 PK를 매핑하므로 재실행해도 일치하는 행과 embedding을 재사용한다. 불일치나 누락된 외래 키가 발견되면 전체 트랜잭션을 되돌린다. pgvector 값과 여러 generated identity를 함께 매핑해야 하므로 이 부분은 Alembic이나 수동 SQL 대신 현재 애플리케이션 모델을 사용하는 명령으로 분리했다.
4. GitHub Actions의 **Reindex**를 수동 실행한다. 워크플로는 `ALL` 모드로 모든 그룹을 정렬된 순서로 처리하고, 성공한 그룹마다 `documentGroupId`를 붙인 corpus reload를 수행한다.
5. 각 그룹의 관리자 상태와 내부 corpus 상태를 확인하고, `HELP_CHATBOT_TEST`의 internal test chat으로 검색 및 답변을 확인한다.

재색인 로그에는 그룹 ID, 결과 코드, 최종 집계만 남기며 응답 전문이나 인증 정보는 출력하지 않는다.
